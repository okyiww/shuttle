## 适用场景

- 用户提供 VoiceNotes 会议标题、会议纪要、转写文本、聊天记录或截图，要求分析“每个人要做什么”。
- 需要将会议行动项转成 AI 项目的 Jira 任务，并默认规划到指定的下一 Sprint。
- 会议中既包含新任务，也包含需要修改、迁移或重构已有 Jira 卡片的事项。
- 需要核对任务归属、避免将讨论项、背景信息或未来规划误建为当前 Sprint 工作。
- 团队中存在尚未开通 Jira 账号的成员，需要记录其工作但暂不创建或分配任务。

## 从 0 到 1 的步骤

1. **确认项目、看板和目标 Sprint**
   - 先确认任务所属 Jira 项目，不能沿用其他项目的 Sprint 规则。
   - 通过 Jira 看板查询 Sprint 列表，识别当前 active Sprint 与下一 future Sprint。
   - 明确用户希望任务进入当前 Sprint、下一 Sprint，还是仅先整理不创建。
   - 示例：AI 项目使用 AI board；后续任务应进入 `AI Platform Sprint 50`，而非 Sitewalk Sprint。

2. **查找会议记录，并优先获取原始转写**
   - 先按完整会议标题搜索 VoiceNotes；若无结果，逐步缩短为核心人名、主题词、业务关键词搜索。
   - 找到录音后，优先调用 transcript 获取原始转写，不应只依赖 summary。
   - 将 summary 用作快速索引，将 transcript 作为任务归属、范围、优先级和措辞的最终依据。
   - 若无法找到录音或转写不完整，明确说明缺失信息并请用户补充链接、录音 UUID、截图或原文。

3. **从转写中提取候选事项**
   - 按以下四类标记内容：
     - **当前 Sprint 可执行工作**：有明确动作、产出或完成目标。
     - **已有卡片修订**：需要改标题、描述、验收标准、优先级、点数、负责人或 Sprint。
     - **未来讨论/待决事项**：例如“之后单独再说”“需确认是否要做”，不可直接当作当前任务。
     - **背景或问题陈述**：用于补充卡片描述，但不自动拆成任务。
   - 为每个候选事项记录原始依据：会议名称、时间、发言原句或转写片段。

4. **按成员重新归属，不按技术关键词机械分配**
   - 以会议中明确的“谁负责什么”为准，而不是根据某项技术内容出现在哪段讨论中推断负责人。
   - 每位成员输出：
     - 当前 Sprint 的明确任务；
     - 涉及的已有卡片；
     - 需澄清项；
     - 明确排除项。
   - 例如：
     - Jarvis：知识库能力尽快上线；“LOA 重构”需另行确认，不自动纳入。
     - Mona：保留并细化原有三张卡的描述与侧重点；迁移既有授权卡；同时新建 MCP OIDC 改造和用户减负实施类任务。
     - Huang Yiwei：继续微服务拆分、架构优化与缺陷修复。
     - liutianya：必须回看 transcript 后再提取，不应因 summary 缺漏而省略。
     - 未开通账号的新同事：仅记录候选工作，不创建 Jira 任务、不分配负责人。

5. **先检索现有 Jira 卡，再决定改卡、迁移或新建**
   - 使用 JQL 按业务关键词、负责人、近期 Sprint 和关联系统检索已有 issue。
   - 对每项工作判断：
     - 已有卡且目标延续：修改描述、验收标准、点数或 Sprint。
     - 已有卡但本 Sprint 工作目标不同：保留旧卡的历史范围，创建新卡。
     - 工作尚未建卡：创建新卡。
     - 只有讨论、依赖或待决结论：不建卡，列为待确认。
   - 特别检查“旧卡是否已有 Story Points”：若有，迁移 Sprint 时保留点数；若无，先请用户确认估算规则，或标记待估算。

6. **处理 Sprint 迁移**
   - 核实 Jira MCP 是否支持编辑 issue 的 Sprint 字段。
   - 若支持：
     - 编辑既有卡，保留 issue key、历史评论、负责人和既有点数；
     - 将卡移入目标 Sprint；
     - 同步更新描述和验收标准，以反映本 Sprint 的实际目标。
   - 若不支持直接修改 Sprint：
     - 明确告知限制；
     - 提供可执行替代方案，例如通过 Jira 界面迁移、使用可用的 issue edit 工具或创建替代卡；
     - 不要私自复制出重复卡。

7. **将每项任务写成可验收的卡片草案**
   - 标题应描述本 Sprint 实际交付，而不是泛泛主题。
   - 描述至少包含背景、目标、关键实现范围和依赖。
   - 验收标准仅写会议已明确或用户确认的内容；对于未知范围，写成待确认项，不要自行补全。
   - 建议字段：
     - 事项类型：故事、任务、缺陷或子任务；
     - 标题；
     - 描述；
     - 验收标准；
     - 负责人；
     - 优先级；
     - Story Points；
     - Sprint；
     - 标签、关联卡与来源。
   - 缺陷任务要额外记录环境、复现路径、实际结果、期望结果和影响范围。

8. **避免把范围外内容写成验收标准**
   - “不纳入附件类 case；留待之后规划”这类内容属于范围界定，不是验收标准。
   - 应单列为“范围外”或“后续事项”，除非该排除条件本身是本次验收必须验证的业务约束。
   - 用户质疑某项范围外描述时，应回溯 transcript：若会议未明确提及，立即移除，而不是为其补充推测性理由。

9. **输出供用户确认的任务清单**
   - 先按人员汇总，不直接创建：
     - 已确认的当前 Sprint 工作；
     - 需要修改或迁移的旧卡；
     - 建议新建的卡；
     - 不创建的事项；
     - 待澄清问题。
   - 对每个待澄清问题说明其影响，例如“是否拆独立卡会影响 Jarvis 的工作范围和估算”。
   - 用户确认后，再执行实际建卡、改卡、迁移 Sprint 和分配负责人操作，并返回 issue key 与链接。

## 踩坑与规避

- **误用错误项目的 Sprint**
  - 不同项目有独立看板和 Sprint。
  - 规避：每次建卡前都重新确认项目 key、board ID 和目标 Sprint ID。

- **只看会议摘要，遗漏关键负责人或限制条件**
  - summary 可能遗漏某个成员、旧卡修改要求或“暂不做”的结论。
  - 规避：用 transcript 校验每位成员的任务；摘要与转写冲突时以转写和用户最新纠正为准。

- **根据技术讨论错误推断负责人**
  - 某人讨论了接口、数据或架构，不代表该人负责对应工作。
  - 规避：只采用明确责任表述；没有明确负责人时标为待确认。

- **把“之后单独讨论”误建为当前 Sprint 任务**
  - 如 LOA 重构、是否拆接口等只是待决话题。
  - 规避：标记为“待决/后续规划”，除非用户明确要求纳入本 Sprint。

- **混淆改旧卡与建新卡**
  - 同一个大主题在不同 Sprint 的交付目标可能不同。
  - 规避：比较旧卡原目标和本 Sprint 目标；目标延续则改卡，目标切换则新建卡并关联旧卡。

- **迁移 Sprint 时丢失既有点数或历史**
  - 复制建卡会丢失讨论记录、历史状态和估算。
  - 规避：优先编辑原 issue 的 Sprint 字段；迁移前记录原点数、负责人和关联关系。

- **给未入系统成员提前建卡或分配**
  - 无账号时无法可靠分配，且用户可能要求暂不创建。
  - 规避：将其工作保留在会议行动项中，显式
